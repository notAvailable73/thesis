0.  PAPER-GROUNDED REASONING (per thesis_implementation_instructions Section 5)
================================================================================
Pre-registered BEFORE any measurement exists, because the axis/tolerance
choices change the answer (verified while designing this step -- see the
worked example in 0.4) and must not be tuned after looking at the numbers.

0.1  Why latency, not just FLOPs, and why CPU is the primary edge axis.
     MobileNetV3 (Howard 2019, PAPER SUMMARIES/CNN_paper_summaries.txt
     Section 5-6) measures "MAdds, params, and real latency on Pixel 1/2/3
     phones (single large core, TFLite)" -- FLOPs alone is explicitly not
     what the paper that names this backbone treats as the deployment
     metric, and this thesis has the same reason to distrust it: MAC
     counters (fvcore included) do not count BatchNorm, ReLU, h-swish,
     hard-sigmoid, pooling or residual adds, which systematically
     understates depthwise/h-swish backbones. RQ4 asks about *edge*
     hardware; the exit criterion mandates CPU as the edge proxy (no Jetson
     Nano access); batch-1 is the edge inference regime (enrolled
     prototypes, one arriving image at a time); single-thread is the
     analogue of Howard 2019's own "single large core" methodology, so this
     repo's numbers stay comparable in KIND to the paper that motivates the
     small backbone.

0.2  Why fvcore (implementation.txt 11.1's spec), not a torch-native
     alternative. torch.utils.flop_counter.FlopCountMode exists and would
     avoid a new dependency, but implementation.txt 11.1 names fvcore
     explicitly, and the user directed this session to follow the spec
     exactly rather than deviate. Consequence handled, not silently
     absorbed: fvcore is not preinstalled on Kaggle/Colab, so it is now a
     line in requirements.txt (every notebook installs from that file, so
     no notebook needed a bespoke `!pip install fvcore` cell) and in
     pyproject.toml. Verified locally (Section 3): fvcore's
     FlopCountAnalysis.total() returns MACs directly (nn.Linear(1000,1000,
     bias=False) at B=1 -> exactly 1,000,000, matching in*out, NOT 2x), so
     `flops_2x_macs` is emitted alongside `macs` in every record purely so
     a reader using the "FLOPs=2*MACs" convention can never misread the
     table by a factor of two.

0.3  Why the reference gate (check_reference_flops) exists and runs FIRST.
     A gate whose failure is silently tolerated is not a gate. Published
     figures used, with provenance (never asserted from general knowledge):
     ResNet-18 "11.7M params / 1.8 GFLOPs" (src/backbones/mobilenetv3.py
     docstring, itself citing PAPER SUMMARIES/CNN_paper_summaries.txt
     Section 8); MobileNetV3-Small "~56-57 MAdds, 2.5M params" (Howard 2019,
     PAPER SUMMARIES/CNN_paper_summaries.txt Section 6). Both figures are
     MAC counts despite being called "FLOPs"/"MAdds" in their sources --
     `check_reference_flops` records `convention_note` explicitly rather
     than silently reconciling the terminology.

0.4  PRE-REGISTERED AXES (written before any Section-4 number exists):
       cost (11.3, Table "latency_vs_auroc")  : CPU, 1 thread, per-image
           (B=1) MEDIAN latency in ms.
       cost (11.4, Table "params_vs_accuracy"): trainable parameters
           (log scale).
       quality                                : ood_auroc__tin_near__<native>
           (vacuity for evidential, msp for softmax) -- the only near-OOD
           pool present in BOTH datasets (cifar100_near is CIFAR-FS-only,
           mini_near is MiniImageNet-only), and the pool RQ3 (step10.txt
           Section 4.6) found the low-data trend on. `ood_auroc_mean` in
           mvt_results.json is NEVER used as the quality axis -- it silently
           aliases the svhn_far value (verified against the committed JSON),
           which is a trap this step deliberately avoids.
       recommended-point rule: the cheapest configuration whose quality is
           within 1.0 pp accuracy / 0.010 AUROC of the panel's best. Chosen
           because it materially changes the answer -- verified on the
           committed grid data that "cheapest within 1.0 pp" and "cheapest
           within one combined CI95" pick DIFFERENT configurations on
           CIFAR-FS 5-shot (mbnet/parallel/softmax @6,928 vs
           r18/parallel/softmax @31,744) -- so the rule had to be fixed
           before, not after, looking.
     Secondary variants (far_svhn_native, near_dataset_native,
     near_tin_best_score, plus the eps-widened frontier) are ALL computed
     and committed to results/pareto_frontier.json, not just the primary,
     so the axis choice is auditable rather than asserted -- see
     scripts/pareto_plots.py's module docstring and the quality-axis audit
     figures (results/pareto_audit/).

0.5  The energy-score correction this step inherits and must not contradict.
     Step 10 (step_writeups/step10.txt Section 4.6, docs/RESULTS_MASTER.md
     Section 3 RQ3) found the non-probabilistic energy score beats
     evidential vacuity in ~70% of matched comparisons across the 40-config
     grid -- superseding the Step 4.5-era "evidential is on par with energy"
     line. Because Step 11's quality axis is a head-vs-head comparison
     (native score per head), this correction determines whether the

     results/pareto_frontier.json) -- Section 4.7/4.9 must report BOTH
     readings, per the pre-registration above, not just the native-score one.

0.6  Deviations from implementation.txt flagged explicitly, none hidden:

2.  WHAT IS MEASURED AND WHAT COLLAPSES
================================================================================
Verified across all 120 grid configs (not assumed): dataset.image_size=224,
dataset.n_way=5, dataset.q_query=15, trainer.type=episodic in EVERY config.
Neither dataset choice nor shot regime changes the model that gets built --
only `(backbone, adapter, head)` does. That is why 12 measurement keys cover
all 40 mvt_results.json leaf cells (8 keys x 4 mvt cells for the PEFT
adapters that run on both datasets/both shots; 4 keys x 2 mvt cells for the
baselines, which exist only on cifar_fs/resnet18).

Shot regime DOES change episode-shaped units (support batch 5 vs 25), so
those are measured at both k_shot=1 and k_shot=5 regardless of which shot the
key's seed-42 reference config happens to be (src/utils/efficiency.py
episode_input_shapes() is called with an explicit override, never the loaded
config's own fixed k_shot).

Units measured per key: per_image (B=1, the headline edge number, via
model.adapter_features); support_1shot / support_5shot (B=5/25, the
amortisable-once enrollment cost); query_batch (B=75, shot-independent);
score_stage_1shot / score_stage_5shot (head + native uncertainty score, from
CACHED features -- this is what turns "evidential uncertainty is free at
inference" from an assertion into a measured ms figure, Section 4.8);
episode_1shot / episode_5shot (the full model.forward_proto, at the same
warmup/measure settings as everything else in this run -- an additivity
check on the component units above it).

4.9  ANSWERS TO SECTION 0'S QUESTIONS -- the RQ4 paragraph
--------------------------------------------------------------------------------
  RQ4: What is the Pareto frontier between inference latency and
  uncertainty quality on edge hardware?

  On the pre-registered primary axis (Kaggle CPU, 1 thread, per-image
  latency vs. native-score near-OOD AUROC), the recommended Pareto point is
  MobileNetV3-Small + parallel bottleneck + evidential head on CIFAR-FS
  (both shot regimes): 11.86ms/image, 6,930 trainable params, AUROC 0.870
  (1-shot) / 0.919 (5-shot). On MiniImageNet the same MobileNetV3-Small
  point sits on the strict cost-quality frontier but falls outside the
  1.0pp/0.010-AUROC tolerance of the panel's best, so the recommended point
  moves to ResNet-18 + parallel bottleneck + evidential (62.38ms, AUROC
  0.870 / 0.958) -- consistent with the MobileNetV3-vs-ResNet-18 accuracy
  gap that step_writeups/step10.txt already found widens specifically on
  MiniImageNet.

  BACKBONE CHOICE, NOT ADAPTER CHOICE, DRIVES LATENCY -- this step's most
  novel measurement, and a clean, quantified finding: ResNet-18 vs
  MobileNetV3-Small at matched adapter (parallel, softmax) is 62.18ms vs
  12.14ms, a 5.12x difference. Meanwhile LoRA vs the parallel bottleneck on
  ResNet-18 -- a 2.58x difference in trainable parameters (12,288 vs
  31,744) -- produces only a 3.9% latency difference (59.76ms vs 62.18ms);
  on MobileNetV3-Small the adapter choice with MORE parameters (LoRA,
  10,752 vs parallel's 6,928) is actually 5.8% FASTER, reversing the naive
  param-implies-latency intuition entirely. Both adapters' parameter deltas
  (tens of thousands) are swamped by the frozen trunk's forward-pass cost
  (2.5M or 11.7M parameters) -- exactly the mechanism Section 0.4's
  pre-registration anticipated, now measured rather than assumed. Practical
  reading: choosing the adapter is an accuracy decision (RQ1, up to +8.3pp);
  choosing the backbone is the latency decision (RQ4, 5.1x).

  Cross-check against Step 8/10: mbnet/parallel/softmax's accuracy
  (90.74%, CIFAR-FS 5-shot, 6,928 params) essentially matches
  r18/full_ft/softmax (90.47%, 11,176,512 params) as already established in
  docs/RESULTS_MASTER.md Section 4.7 claim 2 -- Step 11 adds the missing
  latency side of that comparison: mbnet/parallel/softmax is 12.14ms vs
  full_ft's 61.52ms on the same hardware, a 5.1x latency advantage riding
  alongside the 1,613x parameter advantage already reported, for
  essentially the same accuracy.

  Mode-A/Mode-B counterpoint (4.7): under the primary native-score reading,
  evidential heads anchor every strict frontier in 4.5. Under Mode B
  (softmax gets its best of 3 scores), evidential's frontier presence
  collapses on CIFAR-FS 5-shot to nothing -- the softmax sibling of the
  SAME (backbone, adapter) pair takes its place. This is Step 10's grid-
  wide "energy beats vacuity ~70% of the time" finding, now visible in the
  efficiency-aware view too, not just the accuracy-only OOD tables: the
  claim "put an evidential head on the Pareto-optimal edge configuration
  for better uncertainty" is native-score-conditional, not universal.

  1. "No Jetson Nano access; CPU latency is used as the edge proxy"
     (verbatim, per the exit criterion) -- quantified, not just asserted:
     local-dev-CPU / Kaggle-CPU per_image median ratio, all 12 keys:
     mean 0.825x, range 0.568x-1.289x -- NOT a constant offset, varies by
     up to 2.3x across the 12 architectures. This is direct, measured
     evidence for why Section 8's bug (treating the two machines'
     "cpu_1thread_*" profiles as interchangeable) produced errors as large
     as 47% on some keys and under 1% on others -- a fixed correction
     factor could not have papered over this, only excluding local_cpu
     from the canonical selection (the actual fix) could. The Kaggle CPU
     itself is a hosted-notebook server core, not an edge SoC -- absolute
     milliseconds do not transfer to real edge hardware; ONLY the ratios
     between backbones/adapters are portable, and even those shift with
     kernel quality (Howard 2019: h-swish's latency win depends on an
     optimised fused kernel and "largely disappears" without one, so
     MobileNetV3-Small's real edge advantage is plausibly LARGER than what
     PyTorch eager on a CPU measures here).
  2. Latency and peak-memory are the ONLY numbers in this entire thesis that
     are not byte-reproducible by design -- see
     results/efficiency_table.json's `reproducibility` block, which asserts
     byte-identical reproducibility for the `static` (params/FLOPs) block
     only and states the exemption reason for `measured`. The stability
     re-run (Section 4.3) is the honest substitute for the byte-identical
     check every earlier step's config gets.
  3. MAC counts systematically UNDERSTATE depthwise/h-swish backbones (no
     MAC counter -- fvcore included -- counts BatchNorm/activations/pooling/
     residual adds); the measured MAC ratio between ResNet-18 and
     MobileNetV3-Small therefore OVERSTATES MobileNetV3's advantage relative
     to what the latency measurement shows. Report both together, never the
     MAC ratio alone.
  4. Energy-score asymmetry (0.5): softmax gets 3 uncertainty scores (msp,
     ts_msp, energy) in Step 10's grid; evidential gets 1 (vacuity). Energy
     was never computed on evidential logits. This step's `near_tin_best_
     score` variant is honest about that asymmetry rather than hiding it,
     but does not fix it -- computing energy on evidential logits is the
     cheapest open follow-up (Section 7), requiring no retraining, only a
     re-run of the 120-cell eval.

     step9.txt Section 5 (a test-isolation bug traced by code inspection,
     never confirmed by a logged exclusion count from a real run): every
     `tin_near` AUROC number this step's primary quality axis depends on

  6. MiniImageNet panels have ZERO baseline points (Section 4.6) -- Step

     (scripts/pareto_plots.py), `_eff_primary_latency`
     (scripts/make_master_tables.py), and a closure named `_eff_lat`
     (scripts/make_results_master.py) -- each pick a key's primary-axis
     latency the same naive way:
       for profile, timing in per_image.items():
           if profile.startswith("cpu_1thread_"):
               return profile, timing
     `per_image` is a dict; Python dicts preserve insertion order; and
     scripts/efficiency_table.py's write path is `_deep_merge(existing,
     result)` -- NEW data is merged ONTO the OLD file, so pre-existing keys
     (local_cpu, present in every commit since Section 3's first offline
     run) always sort before whatever a later session adds. Both
     `local_cpu`'s and `kaggle_t4_cpu`'s per-image profile names start with
     "cpu_1thread_" (the thread-count prefix, not the hardware), so ALL
     THREE functions silently picked local_cpu every time, on every commit,
     since Step 11's code first existed -- not a regression introduced by
     8.6's fix, a pre-existing bug that 8.1's crash had (accidentally)
     prevented from ever mattering, because no canonical Kaggle data had
     reached these functions until this session.

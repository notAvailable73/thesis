0.  WHAT THIS DOCUMENT IS (READ FIRST)
--------------------------------------------------------------------------------

proposal.txt is the research vision: the title, the four research questions,
the methodology, the proposed experiments. It does not say WHEN or HOW to
build any of it.

implementation.txt is the step-by-step engineering spec. Its 13 steps each
belong to one of this plan's six phases and each is tagged with the
research question(s) it advances.

THIS document — plan.txt — is the master execution plan. It owns:
  - the mapping from the proposal's four RQs to concrete deliverables
  - the order in which those deliverables get built (six phases)
  - the cut buffer if time runs short (priority-ordered drop list)
  - the current state of the project (what is done, in-progress, not started)

Anything in implementation.txt is a finer-grained breakdown of one or more
phases in this document. When the two disagree, this file wins and the
spec should be updated. progress.txt tracks per-step task completion.

1.  THE THESIS IN ONE PAGE (proposal.txt distilled)
--------------------------------------------------------------------------------

CLAIM:
  Lightweight CNNs (ResNet-18, MobileNetV3-Small, ConvNeXt-Nano) can be
  adapted to new few-shot tasks using <1% of their parameters AND remain
  well-calibrated AND know when an input is out-of-distribution, by
  combining parameter-efficient fine-tuning (Bottleneck adapters, LoRA,
  BitFit) with an evidential Dirichlet head + KL-regularised loss.

WHY IT MATTERS:
  Most PEFT work is on Vision Transformers and reports accuracy only.
  Edge / safety-critical deployments need (a) small parameter footprints,
  (b) honest confidence on familiar inputs, and (c) the ability to flag
  unfamiliar inputs. No prior paper has done a systematic study of those
  three things together on lightweight CNNs.

FOUR RESEARCH QUESTIONS (verbatim from proposal.txt §4):
  RQ1  How does the placement of adapter modules (serial vs. parallel)
       within a CNN bottleneck affect few-shot accuracy vs. parameter count?

  RQ2  Can Evidential Dirichlet Networks (EDN) provide superior calibration
       compared to standard Softmax when fine-tuning with <500 trainable
       parameters?

  RQ3  Does the integration of a Bayesian loss prior improve the detection
       of near-OOD samples in low-data regimes?

  RQ4  What is the Pareto frontier between Inference Latency and Uncertainty
       Quality on edge hardware?

EVERY DELIVERABLE IN THIS PLAN MUST CONNECT TO AT LEAST ONE RQ.
If a piece of work doesn't move an RQ forward, drop it.

PHASE 2 — Real benchmark + episodic protocol (NEXT)
--------------------------------------------------------------------------------

         step_writeups/step4.txt.

             at load time).

5.  MVT VS FULL PROPOSAL — WHAT MUST SHIP, WHAT CAN DROP
--------------------------------------------------------------------------------

The proposal's experimental matrix (3 backbones × 3 PEFT × 4 in-dist × 4
OOD × 2 shots × 3 seeds = 1,728 configurations) is not feasible on Colab
Pro in 12 weeks. The plan therefore distinguishes a Minimum Viable Thesis
from a Full proposal coverage, and commits explicitly to the MVT with a
drop order for everything beyond it.

MINIMUM VIABLE THESIS (mandatory — non-negotiable):
  - All of Phase 1, 2, 6.
  - Phase 3: Bottleneck + LoRA, both heads, placement study (RQ1).
  - Phase 4: SVHN + TinyImageNet (RQ3 with near-OOD).
  - Phase 5: ResNet-18 + MobileNetV3-Small backbones,
             CIFAR-FS + MiniImageNet datasets,
             1-shot + 5-shot,
             efficiency table + Pareto plot (RQ4),
             plus Full-FT and Linear Probe baselines on ResNet-18
             × CIFAR-FS (proposal.txt §6 — non-negotiable).
  This footprint answers all four RQs and produces ~96 PEFT grid runs
  + 24 baseline runs.

EXTENSIONS — kept in priority order; drop FROM THE BOTTOM if time short:
   1. ConvNeXt-Nano backbone           (proposal §5A line 3)
   2. BitFit included in the MVT grid  (already built; adds run-time only)
   3. CUB-200-2011 dataset             (fine-grained few-shot angle)
   4. ISIC medical dataset             (drop first; legal/download risk)
   5. CIFAR-10-C corruption robustness (drop second; nice-to-have)
   6. Gaussian-noise OOD               (drop third; sanity check only)
   7. Jetson Nano latency              (drop fourth; explicit limitation
                                         in the thesis: "no Jetson access;
                                         CPU as edge proxy")

This drop order is binding: if Phase 5 runs over, items are dropped in
this exact sequence, not by personal preference. Maintain RQ coverage
above breadth.

7.  RISKS AND MITIGATIONS (live)
--------------------------------------------------------------------------------

R1  THE CALIBRATION CLAIM REMAINS A TRADE-OFF, NOT A WIN
    Phase 1 confirmed evidential ECE does not beat softmax ECE on the
    stand-in benchmark. If the same holds on real CIFAR-FS + MiniImageNet,
    the thesis claim stays "honest trade-off: small ECE cost, large OOD
    AUROC gain". Do NOT chase a strict ECE win by cherry-picking.

R2  COLAB SESSION LIMITS WILL CUT LONG RUNS
    Phase 5's grid is the danger zone. Save checkpoint every epoch to
    Drive. scripts/train.py must support --resume-from <checkpoint>
    before Phase 5 starts. Resume from checkpoint; never restart from
    scratch.

R3  ONE REPO ONLY
    All work continues in the existing repo. The pre-defence demo state
    is preserved through git tags (when the repo is git-initialised) or
    through step_writeups/step1.txt at minimum. Do not branch into a
    parallel codebase.

R4  THE 600 TEST SEEDS ARE FROZEN
    configs/test_episodes.yaml is treated as committed truth. Every
    phase's evaluation reads from this file. Do not regenerate, do not
    re-seed, do not slice down without recording the slice in the
    metrics JSON.

R5  TIME-PRESSURE DROP ORDER
    Section 5 of this plan defines the drop order. Use it. The
    temptation to drop the writing phase to fit in one more experiment
    is the most common way thesis projects fail; resist it.

R6  EPISODIC TRAINING CAN COLLAPSE SILENTLY
    Phase 2's meta-training is a new failure surface. Add a smoke
    assertion to the trainer: val accuracy after epoch 1 must be > 1/K
    (random). If not, the loop is misconfigured and the run aborts
    before wasting GPU.

R7  CONVNEXT-NANO MAY NOT BE AVAILABLE IN timm
    If timm's ConvNeXt-Nano weights are not pretrained on ImageNet-1k
    or are otherwise unsuitable, swap to EfficientNet-B0 and document
    the swap in Chapter 4. Do not block Phase 5 on a single backbone
    name.
